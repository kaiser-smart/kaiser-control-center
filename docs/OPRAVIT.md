# Opravit — scope, deployment and operations

The `/opravit` module uses the existing individual login and feedback permissions. The global Opravit link carries only the current pathname; query strings and fragments are removed to avoid collecting tokens and personal identifiers. Users provide a plain-language description and optionally one PNG/JPEG up to 5 MiB / 32 megapixels. Identity and timestamps are server-owned. A user can see their own repair reports; managers can see all. Existing ordinary feedback keeps its previous shared visibility.

Reports, attachment hashes, bounded body reads, rate limits (20 per day), deterministic actor/day/content deduplication and access-controlled downloads are enforced on the server. R2 files are served as downloads with the existing authentication and nosniff protection. The initial image check validates type, signature, dimensions and envelope; it is not an antivirus or a full forensic decoder. The screenshot remains untrusted evidence.

## Queue and trust boundaries

`migrations/modular/core/0008_repair_queue.sql` adds only two new CORE tables, two indexes and three triggers. It does not rewrite existing data. Queue creation belongs to the same CORE transaction as the report. Audit events are generated by database triggers in that same database, so state changes cannot lose their audit entry. The existing cross-database workflow preserves the report/evidence audit, and the runner claims only completed workflows.

The hourly workflow processes at most one case at a time. A bounded lease, compare-and-set transitions, globally serial deployment concurrency and a unique run ID prevent duplicate runs and stale callbacks. Expired ambiguous work requires a decision; it is never blindly redeployed. Callbacks need a separate >=32-character token and a run-specific lease, and cannot label a case deployed without deployment/commit/check evidence. Audit state and deployment references are visible to the report owner through Opravit; full operational events remain in CORE.

The generator receives only a JSON observation and optional image. It has no repository write token, production credentials or queue token. Only the resulting CSS bytes leave its runner; Git metadata, scripts, tests, workflows and generated instructions are discarded. A fresh runner reconstructs the diff and applies the trusted gate. Deployment runs on another fresh runner, using the trusted base scripts and exactly the gated CSS patch. Browser tests do not receive production secrets.

## Initial automatic repair scope

The first policy accepts at most eight numeric spacing/type declarations in existing tyre/fleet/feedback/repair CSS rules. Values may change by at most 25% and eight CSS pixels; font sizes stay 12–48px. It forbids new/deleted selectors, JavaScript, network URLs, dependencies, workflows, migrations, data, payment/security/identity selectors, bulk changes and file-mode changes. This intentionally does NOT implement automatic arbitrary business-logic repairs. Outside-scope or unreproducible requests require a separate decision, without automatic deployment.

Before deployment: exact baseline main/production equality, byte-level CSS policy, queue/store/security regressions, existing authentication and feedback regressions, syntax, build and synthetic WebKit phone/tablet/desktop tests. Production checks verify commit identity, CSS hash, route responses and rejection of anonymous protected API access. They do not claim a real authenticated business-operation E2E test or that the reported problem was reproduced in production. The author should verify the original issue after deployment.

The controller records the current successful production deployment, deploys an isolated repair branch, verifies it and fast-forwards main only after success. A failed post-deploy check rolls back only when the active deployment still belongs to that run. It verifies the restored ID, source SHA and old CSS. A later unrelated deployment must not be rolled back. Recovery handles a failed/timed-out job; unverifiable state, failed rollback or a main/production divergence requires a decision.

## Activation prerequisites — do not call this active until verified

1. Apply the additive migration to the verified SMART_ODPADY_CORE binding, after recording a Time Travel bookmark; verify all seven objects and the existing evidence schema.
2. Create a dedicated random `REPAIR_RUNNER_TOKEN` in production Pages secrets and repository Actions secrets. Never copy browser/session credentials into CI.
3. Provide `OPENAI_API_KEY` for the Codex action and a suitably scoped `CLOUDFLARE_API_TOKEN` for the verified account/project's Pages deployment and rollback. Store in GitHub Actions secrets, not source, prompts or job-level environments. The workflow requires all three before claiming work. The current preflight expects repository secrets (not environment-only secrets).
4. Create the `repair-production` GitHub environment without a manual reviewer requirement for this already-authorized narrow policy; keep critical changes outside that policy. Restrict deployment branches to main. Verify GITHUB_TOKEN can create the isolated branch and fast-forward main subject to repository rules.
5. Cloudflare Git production auto-deploy was ON at audit. Before enabling this controller, switch to one deployment owner: disable Cloudflare automatic production deployments and route other production changes through the existing guarded manual release. The controller refuses to deploy while Git production auto-deploy is on; this avoids a second unverified deployment after advancing main. This setting has NOT been changed by this implementation.
6. Set production `REPAIR_AUTOMATION_ENABLED=true` only when prerequisites are verified and the module is deployed. Set repository variable `REPAIR_ENABLED=true` last. Workflow schedule is minute 17 of each hour (UTC; GitHub may delay scheduled runs), independent of a notebook. Do not create a duplicate desktop automation.
7. Execute a controlled manual run, check claim/audit, rejected critical-path patch, accepted CSS patch, immutable evidence, deployment identity and post-deploy checks. Perform an isolated staging rollback drill before claiming live rollback has been exercised. Confirm a subsequent schedule-triggered run before claiming the hourly schedule works.

To stop new automation, set `REPAIR_ENABLED=false` and production `REPAIR_AUTOMATION_ENABLED=false`. Existing report submission remains available. Do not delete audit evidence or restore the entire business database as a routine application rollback: an additive unused queue can remain in place, and whole-database restoration would discard unrelated subsequent writes.
